# Contributing to pouncer

## Development environment

The Nix flake is the single source of truth for the toolchain.

```sh
nix develop          # dev shell with the pinned Rust toolchain; installs the pre-commit hook
nix fmt              # format Rust, Nix, TOML, Python, and Markdown through treefmt
nix flake check      # the same checks CI builds on Linux and macOS
```

CI also runs `cargo test` on a Windows host outside Nix, because the `cfg(windows)` tests exercise `cmd.exe` and
batch-file argument handling that the cross-compiled clippy check cannot.

Development-only inputs live in `dev/flake.nix` with their own lock, so a flake that consumes pouncer never fetches
them. Update them with `nix flake update --flake ./dev`.

## Testing

```sh
cargo nextest run    # unit, property, snapshot, and CLI tests
cargo insta review   # accept or reject changed snapshots after a failing run
cargo mutants        # mutate src/ and report the mutants no test catches
```

Property tests (proptest) state invariants over arbitrary input and sit in a `proptests` module beside the code. When
one fails, proptest records the shrunk case under `proptest-regressions/`; commit that file with the fix so the case
keeps running. Snapshot tests (insta) pin output a property cannot phrase: the overlay as the user sees it, the escape
stream behind it, `--help`, and the startup errors.

`cargo mutants` takes a few minutes and is not a gate. On a pull request, CI runs it on the changed lines only and
comments the result on the pull request (`.forgejo/workflows/mutants.yml`), without failing the run. Treat a missed
mutant as a question about one test: either a test is missing or too weak, or the mutant is equivalent to the original
(for example `|` to `^` on disjoint bits) and is left alone. The terminal setup and the read loop in `picker.rs` need a
real tty, so their mutants are expected to survive.

## Commit conventions (Conventional Commits)

pouncer follows [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) with the project-specific types
below. The type is what `git log` is scanned by: it tells whether a commit moves the CLI surface a user sees, which is
what [CHANGELOG.md](CHANGELOG.md) and the semver bump are decided from.

### Format

```
<type>[!]: <description>

[optional body]

[optional trailer(s)]
```

- **Subject line**: `<type>: <imperative>`, at most 72 characters. Start the description with an imperative verb,
  lowercase, no trailing period. Example: `fix: restore the terminal when the overlay panics`.
- **Scope**: omitted. pouncer is a single crate, so a scope would name the same area on nearly every commit.
- **Breaking changes**: append `!` to the type (`refactor!: rename spoor to pouncer`) when a commit breaks the CLI
  surface: a flag, a default, a preset name, an exit status, or the binary name.
- **Body** (optional but encouraged): explains **why**, not what. The diff already shows what changed. State the
  motivation, the constraint being worked around, or the rejected alternative and why it was rejected. A why that would
  otherwise become a code comment belongs here: the source keeps only why-nots and invariants.
- **Reverts, merges, and other generated commits** may use free form (for example, `Revert "..."` as generated by
  `git revert`).

### Types

| Type       | Use for                                                                |
| ---------- | ---------------------------------------------------------------------- |
| `feat`     | A new user-visible capability: a flag, a preset, an action             |
| `fix`      | A user-visible bug fix                                                 |
| `perf`     | A speedup with no behavior change                                      |
| `refactor` | A code change with no behavior change, including lint fixes            |
| `style`    | Formatting only                                                        |
| `test`     | Tests only                                                             |
| `docs`     | README, `docs/`, `--help` text, man page wording, agent skills         |
| `build`    | `Cargo.toml`, crate packaging, what ships in the crate                 |
| `ci`       | Workflows under `.forgejo/workflows/`                                  |
| `nix`      | `flake.nix`, `flake.lock`, `nix/`, and `dev/`                          |
| `deps`     | `Cargo.lock` and dependency bumps (often generated by Renovate)        |
| `release`  | The version bump and changelog section of a release (`release: X.Y.Z`) |

`feat`, `fix`, and any `!` commit usually come with an entry under Unreleased in [CHANGELOG.md](CHANGELOG.md); the other
types usually do not.

## Releasing

What each check refuses is `tools/release.py`; what each job runs and publishes is `.forgejo/workflows/release.yml` and
`.github/workflows/release-mirror.yml`. This section is the order of operations.

### Release pull request

1. Bump `[package] version` in `Cargo.toml` (semver; before 1.0 a breaking CLI change is a minor) and run
   `cargo update --workspace` so `Cargo.lock` follows.
2. In [CHANGELOG.md](CHANGELOG.md), rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`, open an empty
   `## [Unreleased]` above it, and update the link references at the bottom (`[unreleased]` compares from the new tag,
   `[X.Y.Z]` compares with the previous one).
3. `python3 tools/release.py check vX.Y.Z` passes (in `nix develop`).
4. Commit as `release: X.Y.Z`.

### Tag and watch

- After the merge, `git tag -a vX.Y.Z -m vX.Y.Z <merge commit>` and push the tag. A `-rc.N` tag rehearses the gate and
  the mirror without publishing the crate.
- Forgejo `release.yml`: `verify-tag` gates everything; the release page publishes last, with notes cut from the
  changelog.
- GitHub `release-mirror.yml`: `mirror` waits for that page and copies it, then `crates` uploads the crate unless
  crates.io already has the version, so a failed job is rerun as is. `homebrew` opens a pull request on
  `felis-terminal/homebrew-tap` moving `Formula/pouncer.rb` to the tag's source archive. Once the tap's test-bot passes
  on it, `brew pr-pull` uploads the bottles and lands the formula. When `nix/package.nix` changed since the previous
  release, the pull request is a draft, which `brew pr-pull` skips: bring the formula's install block in line, mark it
  ready, and push the fix or dispatch `brew pr-pull` for it.

### First crates.io publish

Trusted publishing only applies to a crate that already exists, so the `crates` job of the first release fails. After
the Forgejo release is published, at the tag, with no `cargo login` and no credentials file:

1. `cargo publish --dry-run --locked`;
2. `CARGO_REGISTRY_TOKEN=<publish-new token> cargo publish --no-verify --locked`;
3. on crates.io, add a trusted publisher to the crate: repository `felis-terminal/pouncer`, workflow
   `release-mirror.yml`, environment `crates-io`;
4. revoke the token and rerun the `crates` job; it finds the version published and skips.

### First Homebrew formula

`homebrew` only bumps a formula the tap already has, so it fails on the first release too. After the mirror has the tag,
open a pull request on the tap adding `Formula/pouncer.rb` at that tag's archive. Once `brew pr-pull` has landed it,
rerun the `homebrew` job; it finds the formula on the release and skips.
